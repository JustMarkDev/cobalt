source.code runs no job itself. A **runner** is a machine that does: a Mac mini under a desk, a Linux build server, or a hosted provider. You register it, and source.code routes jobs to it and keeps what it reports.

## Register one

```bash
sx runner register mac-mini --labels macos,arm64,xcode-16
```

The answer shows the runner's token once (`sxr_…`). On the machine:

```bash
SX_RUNNER_TOKEN=sxr_… sx runner start
```

It sends a heartbeat every 30 seconds, claims jobs, fetches the repository at the job's commit through the API, runs each step's `run:` and reports it. It needs nothing but the API and a working directory. A person registers runners for themself; an organization's owner or admin for the organization (**Settings, Runners**). `repos` limits a runner to some of the account's repositories; without it, it serves all of them, now and later.

## Which job goes where

A job asks for labels with `runs-on` in its workflow file, a label or a list. A runner takes a job when every label the job asks for is one of the runner's, case ignored: a runner with `macos`, `arm64` and `xcode-16` takes a job asking for `macos`, or for `[macos, xcode-16]`, and never one asking for `linux`. A job with no `runs-on` goes to any runner.

A job no runner can take stays queued and says what it waits for ("Waiting for a runner with: macos, xcode-16"), on the run page, in repository settings and in the inbox of whoever started the run.

A runner holds at most `concurrency` jobs at once (1 by default), counting jobs that wait on someone. A claimed job is leased for 15 minutes; every report and heartbeat extends it. A runner silent for 90 seconds is shown offline, and when its lease runs out its job goes back to the queue with a note on the run.

## Hosted providers

A provider such as Blacksmith or Depot registers the same way, as `kind: hosted` with `provider: blacksmith` and the labels it offers. Its adapter claims a job with the runner token, asks the provider to run it, and reports the result. There is no provider-specific table or endpoint.

## What a runner token can do

Read the repositories the runner serves, claim their jobs and report them. It cannot push, open changes, read issues or secret values, manage runners or make tokens. Revoking the runner disables it and its token in the same write; its next request is refused.

Labels are what the machine says it offers; nobody checks them. A runner that takes a job it cannot run fails it, as in any CI. If code from outside your team runs on a runner, give it a machine or container of its own.

## Steps that wait

A step can pause for a person, an approval, or an outside agent, and resume with how it ended:

```bash
sx pipeline wait 1839 --job 1 --step 3 --kind agent --reason "Update the docs"
sx pipeline resume 1839 --job 1 --step 3 --status success --note "docs updated"
```

A waiting job keeps its runner and is never handed to another. A person it waits on is told in their inbox. A wait ends at `expires_at`, 7 days by default and 30 at most; if nobody resumes it by then, the step and the run fail. `sx handoff run:1839` hands a waiting run to an orchestrator with the exact resume command in its prompt. The agent resumes it under the login of the machine it runs on; no token travels in the prompt.
