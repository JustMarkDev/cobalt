The repository holds the schema: `.env.schema` names each variable, its type, whether it is secret, and which environments need it. Reviewers can see a variable exists without seeing its value. No value is ever committed, so a clone carries none.

The values live on source.code, sealed.

## Who reads values

**The team, and nobody else.** The team is everyone who can write to the repository through its owner: the person who owns it, or **every member of the organization** that owns it, and the teams given write access. Organization membership is secret access: invite to an organization only people you would give its production credentials, and use an outside team with read access for anyone else. Everyone else who can read the repository sees names and never a value: not on the page, not in a clone, not through the API (`forbidden`). A collaborator added to one repository writes code there but reads no values.

Values follow the team, not a machine. Sign in on a new laptop with `sx auth login` and the values are there; there are no keys to copy between machines and nothing to re-encrypt when someone joins. When someone leaves the team, they stop reading at once. When the repository moves to another account, its values do not: they are cleared in the same step, and the new owner sets its own. Rotate what they could have read at each provider; the audit log says what that was.

A signed-in page never receives values, so a script running in the page cannot read them. Values reach a machine's login, and from there one process at a time ([Secrets for agents](/docs/concepts/agent-secrets)).

## How they are kept

- Each value is sealed with AES-256-GCM under a key that belongs to one repository, derived from the server's master key and the repository's id.
- A sealed value is bound to its repository, environment and name. Moved to another slot, it fails to open rather than answering with the wrong secret, and the attempt is logged.
- Without a master key (`SX_SECRETS_KEY`) the server keeps no values at all and says so (`secrets_unavailable`).
- A server can refuse values to machine sign-ins altogether with `SX_DEVICE_DECRYPT=0`; machines then sign in without `secrets:decrypt`. A signed-in page can never make itself a token that reads values.
- Setting a value sends it once over TLS; it is sealed on arrival and never answered back. Setting a production value from a token needs the same confirmation as reading one.
- Responses with values are never cached (`Cache-Control: no-store`), and the operation takes no `Idempotency-Key`, so no copy is kept for a retry.

## Production

Production values need a confirmation for the exact login that asks, given from a page you are signed in to. See [Secrets for agents](/docs/concepts/agent-secrets#production-waits-for-you).

## The audit log

Every set, read, confirmation and refused seal is in **Settings, Secrets**, with who did it, on which machine, through which tool and model.

## Files

A value can be a whole file, up to 64 KiB: a signing key, a service account's JSON, a `.p8`. No third-party tool is involved; it is sealed like any other value.

```bash
sx env set GOOGLE_SERVICES_JSON - --env production < google-services.json
sx env run -- sh -c 'printf %s "$GOOGLE_SERVICES_JSON" > google-services.json && ./build'
```

To keep a file that does belong in git visible to only some people, use a [path access rule](/docs/concepts/access-rules) instead.
