Flags that work on every command:

| Flag                    | Meaning                                                                 |
| ----------------------- | ----------------------------------------------------------------------- |
| `-R, --repo owner/name` | Which repository. Default: your git remote, then `CB_REPO`.             |
| `-A, --account handle`  | Act as this account. See [Accounts](/docs/cli/authentication#accounts). |
| `-j, --json`            | JSON output. This is the default when output is piped.                  |
| `-n, --dry-run`         | Say what would happen and change nothing.                               |
| `--no-color`            | Plain output. `NO_COLOR` works too.                                     |
| `-h, --help`            | Help for the command.                                                   |

## repo

```bash
cb repo list [--all]
cb repo view
cb repo create notes --private --description "Scratch notes"
cb repo create northwind/tools
cb repo clone dana/gitfs
```

`repo list` shows the repositories of the account you act as. `--all` shows every account you can act as. `repo create` takes a bare name, which goes in the account you act as, or `owner/name`. It returns `created: false` when the repository already exists, and exits `5` if you are only a member of that organization.

`repo clone` prints the command, with your host's HTTPS address. Git asks for a username (anything) and a token as the password.

## import

```bash
cb import github dana/notes
cb import https://gitlab.com/dana/zine --as northwind/zine --private
cb import list
```

`import` makes the repository here and keeps pulling from the original through a mirror, until you `cb mirror remove` it. It takes GitHub, GitLab, Codeberg and Gitea, as `host owner/name` or as the repository's address. The repository goes in the account you act as under its own name; `--as` picks another name or `owner/name`. Importing the same repository again returns `created: false`. `import list` shows what you imported and how each mirror is doing.

## account

```bash
cb account list
cb account current
cb account switch <handle>
```

`list` shows every account you can act as with your role and which is in use. `switch` is saved in your settings and is safe to repeat: `switched: false` means you were already there. For one command, pass `-A handle`.

## change

```bash
cb change list [--all]
cb change view [id]
cb change create [--draft] [--branch b] [--title t] [--base main]
cb change land [id]
cb change checkout <id>
```

`change create` needs nothing from you. Title defaults to your last commit and base to `change.base`. Running it again for the same branch returns `action: "patch_set_added"` and the same change.

Changes are named by number, `216`, the same number the API and the web use. With no number, `change view` and `change land` use the open change for your current branch. `change land` lands exactly the tree it just read, so nothing lands that was not looked at.

`change land` exits `5` when policy blocks it:

```json
{
  "error": {
    "code": "policy_blocked",
    "message": "#216 cannot land: ci/test is running; 1 high finding unresolved.",
    "hint": "cb change view shows each requirement. cb policy explain says which rule asked for it."
  }
}
```

## issue

```bash
cb issue list [--state open|closed|all]
cb issue view 4
cb issue create "Crash on empty repo" --label bug,docs
cb issue close 4
```

Creating an issue with the same title as an open one returns the open one.

## env

```bash
cb env list --env production
echo "$VALUE" | cb env set STRIPE_KEY - --env production
cb env run --env development -- bun test
cb env pull --env development --plaintext
cb env confirmations
```

`env list` shows names, kinds and whether each environment has a value. It never prints a value. `env run` puts values into one process and scrubs its output; `env pull` writes a plaintext file only with `--plaintext`. Production waits until you confirm the login on a signed-in page; `env confirmations` lists what is waiting. See [Secrets](/docs/concepts/secrets).

## policy

```bash
cb policy check 216
cb policy explain 216
```

Both exit `5` when blocked. `explain` lists each requirement.

## context

```bash
cb context
```

One JSON document for an agent: the repository, open changes with what blocks them, open issues, policy summary and the env schema. No secret values.

## Every command is an API call

`cb` is a client of the [HTTP API](/docs/api). The JSON a command prints is what the API returned (plus a few fields `cb` adds, such as `action` and `blockers`), and an error is the API's error with its `code`, `hint` and exit code. Anything `cb` can do, a script can do with `curl`.
