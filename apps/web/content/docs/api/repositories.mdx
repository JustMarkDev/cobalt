The [reference](/docs/api/reference/repositories) lists every operation. This page is about how they fit together.

## Rename, hide, delete

```bash
cbcurl -X PATCH $CB/repos/dana/gitfs -H "If-Match: $ETAG" \
  -d '{"name":"gitfs-core","description":"A filesystem over git","visibility":"private"}'
```

Read the repository first and send the `ETag` it returned as `If-Match`; it is a value like `W/"rep_…"`, not a number.

Only owners of the account and admins of the organization can do this. A token limited to repositories can change a repository's description, visibility and default branch, but cannot rename or delete one, or change its maintainers: those change which repository the token means or who can write to it.

**Changing maintainers is an access-control change.** Each name must be a person. Adding one also grants repository write access, and removing one revokes the write access that the maintainer list granted, unless the person has another grant. The same applies when a repository is created with `maintainers`.

**A rename keeps the old address working.** `GET /repos/dana/gitfs` answers `308` with the new address in `Location` and `Cb-Renamed-From`, on every method, so a client that follows redirects never notices. The repository keeps its `rep_` id, and webhooks, mirrors, variables, team access and runs move with it. Taking a name that exists answers `invalid_state` (409).

**Making a repository private hides it at once** from everyone who could only see it because it was public, in lists, in search and in events.

**Deleting is permanent and asks twice.** You must repeat the full name:

```bash
cbcurl -X DELETE "$CB/repos/dana/gitfs-core?confirm=dana/gitfs-core"   # 204
```

Without it you get `invalid_request` and a hint, so a mistyped path cannot delete the wrong thing. Webhooks, mirrors, variables and runs go with it; their tokens stop working. The events it wrote stay in the log, readable by the owners and admins of the account. The name can be used again.

Each of these writes an event (`repo.updated`, `repo.deleted`) and supports `?dry_run=true`.

## Teams

A team is a named group of people in an organization. Give it repositories of that organization and its members can read or write them, **whether or not they belong to the organization**. That is how you let a contractor into one private repository and nothing else.

```bash
cbcurl -X POST $CB/accounts/northwind/teams -d '{"slug":"support","name":"Support"}'
cbcurl -X PUT  $CB/accounts/northwind/teams/support/members/ines
cbcurl -X PUT  $CB/accounts/northwind/teams/support/repos/northwind/relay -d '{"permission":"read"}'
```

- `read` lets members read the repository, including a private one. `write` lets them change it. Setting it again changes the permission.
- Taking a person out of the team, deleting the team or taking the repository away removes the access at once.
- Only members of the organization can see its teams; everyone else gets `404`. Only owners and admins change them, and a token limited to repositories can neither read nor change them.
- A team has at most 500 members and reaches only its own organization's repositories.

Team access is read from the team on every request, so there is nothing to refresh.

## Git data

```bash
cbcurl "$CB/repos/dana/gitfs/git/tree?path=src"           # a directory
cbcurl "$CB/repos/dana/gitfs/git/blob?path=README.md"     # a file, as text or base64
cbcurl "$CB/repos/dana/gitfs/git/raw?path=logo.png" -o logo.png
cbcurl "$CB/repos/dana/gitfs/git/commits?limit=20"        # history, newest first
cbcurl "$CB/repos/dana/gitfs/git/commits/3c2646a"         # one commit
cbcurl "$CB/repos/dana/gitfs/git/commits/3c2646a/diff"    # what it changed
cbcurl "$CB/repos/dana/gitfs/git/commits?path=src/refs.rs" # history of one file
cbcurl "$CB/repos/dana/gitfs/git/blame?path=src/refs.rs"  # who last wrote each line
cbcurl "$CB/repos/dana/gitfs/git/compare?base=main&head=fix-refs" # merge base and diff
```

The store answers these itself, so an agent or a CI job never needs a clone to ask who wrote a line, how two commits relate, or what a branch changed. `compare` reads like `git diff base...head`: `merge_base` is the commit where the two histories split.

- `ref` takes a branch or a commit id. The tree answers with the full commit id it resolved to, so you can keep reading the same snapshot while the branch moves.
- Anything addressed by a full commit id never changes, so it is answered with `Cache-Control: private, max-age=31536000, immutable`. It is `private` on purpose: whether a repository is public is not the cache's business.
- `blob` returns files up to 1 MiB as JSON. `raw` returns the bytes as an attachment with `nosniff` and a sandboxing Content-Security-Policy, so a file in a repository can never run in the page that opens it.
- A diff is cut at 64 KB per file, with `truncated: true` when it was.
- History follows a cursor through the newest 1,000 commits. A new commit at the head does not move your place.
- Reading a repository you cannot see answers `404`, never `403`.

The preview serves these from the sample repositories `dana/gitfs` and `dana/tinyqueue`. Repositories created through the API have no history yet and answer `404`; pushing is not part of the API.
